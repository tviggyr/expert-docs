# Expert Similar Products — PHASE 3: відбір кандидатів і розрахунок схожості

PHASE 3 реалізує незалежний від store view прикладний шар для розрахунку базової схожості. Вона не зберігає результати в БД і не показує їх на вітрині.

Основний вхідний контракт:

```php
SimilarityEngineInterface::rankForProduct(int $productId): array
```

Результат складається з `RankedSimilarProductInterface`: `product_id`, score `0..100`, ранг та кількість оцінених правил.

## Відбір кандидатів

Для Similar Products діє інваріант проєкту: один товар належить рівно одній категорії.

```text
Вихідний товар
  ↓
його єдина категорія
  ↓
кандидати лише з тієї самої категорії
```

`SourceProductCategoryResolver` поводиться так:

| Кількість категорій у вихідного товару | Результат |
|---|---|
| 0 | порожній ранжований результат |
| 1 | звичайний розрахунок |
| більше 1 | `InputException`; система не обирає primary, deepest або поточну категорію мовчки |

`SameCategoryCandidateSelector` застосовує лише жорсткі фільтри:

- виключає сам вихідний товар;
- залишає тільки увімкнені товари;
- залишає тільки товари, видимі як самостійні товари каталогу;
- залишає тільки товари тієї самої категорії.

Бренд, Attribute Set, значення правил, price, stock/MSI та стандартні Magento product links не впливають на набір кандидатів. Товар, якого немає в наявності, на цьому етапі не виключається.

## Ефективні правила та значення характеристик

`SimilarityEngine` отримує правила категорії один раз через `EffectiveRuleResolverInterface`. Він не читає таблиці глобальних і категорійних правил і не повторює логіку `override`, `disabled` або успадкування.

Якщо ефективні правила порожні, результат порожній.

`ProductAttributeValueLoader` однією пакетною колекцією товарів завантажує лише потрібні `attribute_code` для вихідного товару та всього набору кандидатів. Він використовує `store_id = 0`, тому базова схожість не залежить від поточного store view вітрини.

`Attribute Set` не бере участі в score: він потрібен лише для вибору під час налаштування категорії.

## Способи порівняння характеристик

### `exact` («Точний збіг») — точний збіг

`exact` відповідає на питання: **«Значення однакові?»**

Приклади:

```text
Бренд:
Samsung ↔ Samsung  → збіг
Samsung ↔ LG       → немає збігу

Тип завантаження:
фронтальне ↔ фронтальне → збіг
фронтальне ↔ вертикальне → немає збігу

Числа:
8 кг ↔ 8 кг → збіг
8 кг ↔ 9 кг → немає збігу
```

Використовуйте `exact` для бренду, типу, технології, роздільної здатності, булевих характеристик та значень, де важлива саме ідентичність. Для чисел порівняння є числовим: `10`, `10.0` і `10.00` вважаються однаковими. Для тексту видаляються лише пробіли на початку та в кінці; нечітке зіставлення та приведення регістру не виконуються.

### `proximity` («Близькість») — числова близькість

`proximity` відповідає на питання: **«Наскільки близькі числові значення?»**

Використовуйте його для максимального завантаження, кг, діагоналі, потужності, об’єму, ємності, ваги, частоти та інших числових характеристик.

`proximity` потребує `tolerance_percent` у межах `0 < tolerance_percent <= 100`.

Приклад: вихідний товар має максимальне завантаження `8 кг`, а допуск дорівнює `20%`.

- `8 кг` отримує максимальний бал за критерій;
- `7 кг` і `9 кг` отримують частковий бал;
- значення за межами допуску отримують `0`.

Поточна формула:

```text
distance = abs(candidate - source)

toleranceAbsolute =
    abs(source) * tolerance_percent / 100

criterionScore =
    max(0, 1 - distance / toleranceAbsolute)
```

Якщо `source = 0`, діє окремий контракт: `candidate = 0` дає `1`, а будь-яке інше значення — `0`. Це виключає штучний epsilon і ділення на нуль.

### `intersection` («Перетин значень») — перетин наборів

`intersection` відповідає на питання: **«Наскільки перетинаються набори значень?»**

Він використовується для `multiselect`. Значення нормалізуються до унікального набору непорожніх скалярних значень; порядок і дублікати не впливають на результат.

```text
Source: A, B

Candidate: A, B  → 1.0
Candidate: A     → 0.5
Candidate: A, C  → 1/3
Candidate: C     → 0
```

Використовується коефіцієнт Жаккара:

```text
|A ∩ B|
-------
|A ∪ B|
```

Чим більше спільних значень, тим більший score за критерієм.

## Як вибрати comparator

| Тип характеристики | Рекомендований comparator | Приклад |
|---|---|---|
| Бренд | `exact` («Точний збіг») | Samsung = Samsung |
| Тип завантаження | `exact` («Точний збіг») | фронтальне = фронтальне |
| Роздільна здатність | `exact` («Точний збіг») | 4K = 4K |
| Максимальне завантаження, кг | `proximity` («Близькість») | 8 кг близько до 9 кг |
| Діагональ | `proximity` («Близькість») | 55" близько до 50" |
| Набір функцій / `multiselect` | `intersection` («Перетин значень») | порівняння спільних значень |

Фактично доступні comparator визначає `AttributeEligibility`; Admin і REST не повинні створювати власну таблицю сумісності.

## Важливість правил

Адміністратор налаштовує лише три значення:

| Важливість | Внутрішня вага | Значення |
|---|---:|---|
| `high` («Висока») | 3 | характеристика сильніше впливає на score |
| `normal` («Звичайна») | 2 | звичайний вплив |
| `low` («Низька») | 1 | додатковий, другорядний сигнал |

Числова вага не налаштовується через Admin. `position` не є вагою: він визначає стабільний порядок правил і критеріїв у діагностичних даних.

## Підсумковий score

Кожен comparator повертає `criterionScore` від `0` до `1`. Підсумковий score нормалізується до `0..100`:

```text
SUM(weight × criterionScore)
---------------------------- × 100
SUM(weight для оцінюваних правил)
```

Приклад:

```text
Бренд: normal («Звичайна»), weight = 2, exact («Точний збіг») score = 1
Максимальне завантаження: high («Висока»), weight = 3,
proximity («Близькість») score = 0.5

(2 × 1 + 3 × 0.5) / (2 + 3) × 100 = 70
```

Тому `high` впливає сильніше за `normal`, а `normal` — сильніше за `low`, але score не залежить від простої кількості налаштованих правил.

## Як формується пріоритет схожих товарів

1. Система бере кандидатів лише з тієї самої category, що й вихідний товар.
2. Для кожного effective rule comparator обчислює `criterionScore`: `exact`
   («Точний збіг») повертає `0` або `1`, а `proximity` («Близькість») та
   `intersection` («Перетин значень») — значення від `0` до `1`.
3. `criterionScore` множиться на importance weight: `high` («Висока») = 3,
   `normal` («Звичайна») = 2, `low` («Низька») = 1.
4. Сума нормалізується до score `0..100`:

   ```text
   SUM(weight × criterionScore)
   ---------------------------- × 100
   SUM(weight для оцінюваних правил)
   ```

5. Кандидати сортуються за `score DESC`, потім за `product_id ASC`.
6. Persistent index зберігає TOP 30 цього базового порядку.
7. Runtime окремо застосовує salable-first partition, rotation і `LIMIT 8`;
   ці кроки не перераховують базовий score.

Приклад для source товару `Samsung / фронтальна / білий`:

```text
Бренд = high («Висока», 3), comparator = exact («Точний збіг»)
Тип = normal («Звичайна», 2), comparator = exact («Точний збіг»)
Колір = low («Низька», 1), comparator = exact («Точний збіг»)
```

Кандидат A: `Samsung / фронтальна / чорний`:

```text
(3 × 1 + 2 × 1 + 1 × 0) / 6 × 100 = 83.33
```

Кандидат B: `LG / фронтальна / білий`:

```text
(3 × 0 + 2 × 1 + 1 × 1) / 6 × 100 = 50
```

Бренд не є жорстким фільтром: інший бренд не виключає товар, а отримує `0`
лише за бренд. `position` також не є вагою — він задає стабільний порядок
правил. Якщо source не має значення критерію, це правило не входить до
знаменника. Якщо значення немає у candidate, candidate отримує `0` за цей
критерій, а його вага лишається у знаменнику.

## Відсутні значення

Семантика відсутніх значень є частиною розрахунку:

- якщо у вихідного товару немає придатного значення критерію, правило не потрапляє в знаменник; кандидат не втрачає балів за характеристику, якої немає у вихідного товару;
- якщо вихідний товар має значення, а кандидат не має його або має непридатне значення, `criterionScore = 0`, але вага лишається у знаменнику;
- якщо вихідний товар не має придатних значень для жодного ефективного правила, `SimilarityEngine` повертає порожній результат.

Наприклад, якщо вихідний товар не має значення «Діагональ», це правило не змінює score жодного кандидата. Якщо вихідний товар має `55`, а кандидат не має значення, він отримує `0` за цей критерій.

## Стабільне ранжування і продуктивність

Кандидати сортуються детерміновано:

```text
score DESC
product_id ASC
```

Ранг починається з `1`. Кандидат зі score `0` може лишатися внизу ранжованого результату, якщо у вихідного товару є хоча б один оцінюваний критерій. Мінімального порогу score у PHASE 3 немає.

Для продуктивності ефективні правила отримуються один раз, EAV-значення завантажуються пакетно, немає циклу `ProductRepository` або `AttributeRepository` на кожного кандидата. Порівняння в пам’яті має очікувану складність `O(candidates × rules)`.

## Що не реалізовано

Поточний модуль не має:

- постійного індексу схожості;
- Magento Indexer, MView, індексації за cron або інкрементальної переіндексації;
- runtime-ранжування за ціною;
- MSI-ранжування за наявністю;
- rotation;
- PDP block або Hyvä-вітрини;
- Similar Products API кошика;
- Accessories;
- інтеграції з Proxy або Filter Settings.

## Подальший розвиток

Наступні фази можуть використати `SimilarityEngineInterface` для індексації або runtime-представлення, але ці можливості ще не реалізовані.
